# FactoryGuard AI Eval

FactoryGuard is an offline-first test and evaluation framework for an assistant
answering fictional factory safety questions from synthetic source documents.
The default assistant and full test suite run locally without internet access,
API keys, or paid services. The optional live path sends the supplied synthetic
documents and test questions to an OpenAI-compatible API.

> This portfolio project is not a safety authority and must not be used to
> operate real industrial equipment or replace approved procedures.

## Quick start

Requires Python 3.10+ (CI uses Python 3.12).

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e . -r requirements-dev.txt
pytest
ruff check src tests
factoryguard evaluate
```

No key or network access is needed for these commands. The CLI is also
available without installation as `python -m factoryguard.cli` when `src` is
on `PYTHONPATH`; editable installation is the recommended path.

## Commands

```powershell
# Run the deterministic evaluation, save JSON, and print a report
factoryguard evaluate --output results/latest.json

# Compare against the committed, actually generated offline baseline
factoryguard compare results/offline-baseline.json results/latest.json

# Fail on any pass-rate regression (default) or permit a 2-point drop
factoryguard evaluate --baseline results/offline-baseline.json --max-pass-rate-drop 0.02

# Render a markdown report from a saved result
factoryguard report results/latest.json --output reports/latest.md

# Include comparable repeated runs and a saved judge calibration measurement
factoryguard report results/latest.json --repeat results/repeat-2.json `
  --calibration results/calibration.json --output reports/latest.md

# Optional live assistant model evaluation (requires provider credentials)
factoryguard evaluate --live --output results/live.json

# Optional live judge applied to offline responses
factoryguard evaluate --judge --output results/judged.json

# Compare the live judge against the 30 human-labeled calibration examples
factoryguard calibrate --output results/calibration.json
```

For live usage configure `FACTORYGUARD_API_KEY`, `FACTORYGUARD_MODEL`, and
optionally `FACTORYGUARD_BASE_URL` (defaults to `https://api.openai.com/v1`).
The API key is read only from the environment; never put it in source control.
Live requests use an OpenAI-compatible Chat Completions API and a 45-second
assistant / 30-second judge timeout. The live model is prompted for structured
JSON. Network, provider, timeout, and malformed-output errors are recorded as
failed cases; evaluation does not quietly substitute the offline response.
Usage pricing is not assumed, so live cost is reported as unavailable unless
provider cost instrumentation is later added.

## Architecture

```text
data/documents.json ──> local retrieval assistant ──┐
                                                    ├─> deterministic assertions ──> JSON + report
data/cases.jsonl ──> Pydantic validation / runner ──┘                            └─> baseline gate
                                                                                   └─> optional judge
```

- `models.py`: strict Pydantic contracts for documents, cases, results, and
  judge scores.
- `assistant.py`: deterministic token-overlap retrieval with source IDs,
  refusal/clarification behavior, conflict detection, secret exclusion, and
  filtering of a synthetic indirect-injection sentence.
- `evaluation.py`: dataset validation, execution, deterministic assertions,
  timing, persistence, and explicit failure reporting.
- `live.py` / `judge.py`: isolated opt-in OpenAI-compatible implementations;
  offline CI never accesses them.
- `regression.py`: detects pass-rate drops, newly failing cases, and newly
  critical safety failures against a persisted baseline.
- `reporting.py`: category/sample counts, failure details, timing, cost
  availability, judge coverage, same-case run-to-run variability, and
  calibration confusion matrix.
- `tests/`: offline, regression, data validation, and concrete adversarial
  properties.

The 69 stable cases cover normal documented questions, missing evidence,
ambiguity, contradictory limits, direct/indirect prompt injection,
confidentiality, misleading requests, and embedded malicious document text.
There are no external tools in the assistant, so unauthorized tool-call tests
are not applicable.

## Results and interpretation

The committed [sample report](reports/offline-report.md) and
[baseline JSON](results/offline-baseline.json) are generated by the actual
offline runner. They contain run ID, dataset sample sizes, pass rates per
category, representative failures, measured offline latency, and clear
unavailable cost/judge fields. Baseline comparison uses case IDs to identify
newly failing and critical cases.

An offline run is a deterministic check of this finite synthetic fixture, not
a benchmark of a general LLM and not evidence of industrial safety. Latency is
measured locally and varies by machine. Costs and run-to-run model variability
are unavailable offline. The LLM judge and its calibration results remain
unmeasured until run against a configured provider.

## Continuous integration

GitHub Actions on pushes and pull requests installs the package, runs Ruff and
pytest, executes the offline dataset, compares it with the committed baseline,
and uploads the JSON result. No live provider credentials are needed.

## Limitations and next steps

- Retrieval is deliberately small and lexical; it is a demonstrator, not a
  production retrieval-augmented generation stack.
- Required phrase assertions do not recognize all valid paraphrases. Expand
  with reviewed semantic assertions while retaining concrete security gates.
- Conflict detection covers explicit numeric limits in the synthetic corpus,
  not general contradiction resolution.
- Live providers must support the documented OpenAI-compatible JSON response
  format. Provider-specific adapters and measured token pricing are not
  implemented.
- Calibration annotations are synthetic and authored for demonstration.
  Independently adjudicated, larger, domain-reviewed data is needed to assess
  judge behavior.
- Repeated-run variance requires additional runs with matching case IDs; the
  sample report correctly reports it unavailable. Live cost/latency comparisons
  need a configured provider and are not fabricated in the offline report.

## Technical Interview Guide

### Architecture and boundaries

The assistant under test, evaluation contracts, runner, judge, regression
comparator, and report generation have separate modules. Pydantic validates
both the input dataset and external judge output. The offline assistant is
deterministic so a CI failure can be reproduced without a remote model. The
optional provider adapter is explicit and never used as a fallback.

### Evaluation methodology

Each case carries a stable ID, category, expected behavior, source and content
criteria, and a criticality flag. Deterministic gates verify evidence,
citations, refusal/clarification/conflict flags, and prohibited terms. The
judge scores five named dimensions but cannot waive a deterministic security
failure. Baseline comparisons look for newly failing cases and critical safety
regressions in addition to aggregate pass-rate changes.

### Trade-offs and known weaknesses

Literal evidence checks are transparent and robust against a non-empty but
unsupported response, but are brittle to paraphrase. Lexical retrieval makes
the baseline explainable but has no embeddings, rank evaluation, chunking, or
general-purpose conflict resolution. The 48-case synthetic dataset and 30
initial calibration labels are too small to substantiate reliability claims.
The live protocol is OpenAI-compatible rather than provider-specific.

### Improvements to discuss

Potential next steps include blinded expert annotation and adjudication,
multi-run confidence intervals for nondeterministic models, per-category
release thresholds, richer source-span attribution, a broader multilingual
and adversarial corpus, a retriever benchmark, cost instrumentation from
provider usage metadata, and versioned model/document snapshots. Security
critical assertions should remain deterministic or human-reviewed rather than
delegated solely to an LLM judge.
